# StarFur Forge: Resident Intelligence Platform Project Brief

This document is a fact-dense companion to ROADMAP.md for document-intake and retrieval testing. It describes the current StarFur Forge architecture, completed foundation, active implementation order, future systems, and intended end state. ROADMAP.md remains authoritative; this article is a structured test corpus, not a second source of truth.

## Mission and product identity

StarFur Forge is a local-first Resident Intelligence Platform with an executable Persona Runtime. It is intended to feel like a persistent resident living in the user's computing environment rather than a chatbot that disappears between sessions. One or more companions should remember responsibly, develop bounded interests and verified skills, perceive the user's world only with permission, and assist through transparent state, tools, and replaceable intelligence providers.

The language model is a replaceable reasoning provider. The companion is the continuity system around the model. A persona is not merely a giant prompt: it is a validated runtime composed of static identity, dynamic personality, momentary state, behavior rules, attention selection, memory visibility, and context rendering. Core controls factual grounding, safety, provenance, permissions, state mutation, and canonical memory. Persona text controls presentation and tone but cannot replace policy.

The central product question is whether a feature makes the companion feel more like a persistent resident rather than a transient chatbot. The long-term product is a full resident desktop experience: a lightweight apartment or dashboard where a companion visibly lives, idles, works, sleeps, reacts to user presence and absence, shows current activity, and persists independently of whichever model is loaded.

## Core architecture and boundaries

The shared environment contains StarFur Core. Core owns canonical memory, provenance, retrieval, associations, persona runtime state, behavior and attention rules, provider adapters, capability routing, tools, permissions, scheduling, learning sandboxes, adventure state, diagnostics, and package validation. Presentation clients include terminal Assistant Mode, the local OpenAI-compatible API, OpenWebUI, a future Textual TUI, a dashboard, a desktop apartment, a phone surface, and eventually a Steam product. Clients must use shared application services instead of duplicating orchestration.

Architectural invariants are strict. Persona, memory, policy, retrieval, providers, tools, permissions, and presentation remain separate concerns. Persona packages are declarative and validated; user-provided files do not execute arbitrary code. Static identity is stable and user controlled. Dynamic traits change slowly through explicit, explainable transitions. Momentary state changes per turn or event and decays or expires. Runtime state never silently rewrites canonical memories. Learning records observations, evidence, outcomes, and confidence separately from source memories. Only bounded relevant state enters model context. The model never receives an unbounded internal database or hidden chain of thought.

Behavior rules may shape warmth, verbosity, humor, curiosity, initiative, interruption style, examples, and clarification behavior, but never override engine policy, invent facts, expose private state, or mutate canonical memory. Autonomous work requires a sandbox, resource limits, logs, and user-visible outcomes. No background task may change production files, memories, or external systems without permission. Shared Core memory can serve multiple personas, while persona-specific state is namespaced and cannot alter shared factual truth. Tests should use temporary SQLite, fake providers, fake collections, and deterministic clocks.

## Completed manuscript and lore foundation

The Crown of Claws writing corpus uses prechunker-generated `canon/chapters/**/*.md` as the authoritative structured-analysis input. The completed pipeline is Prechunker -> Mr. Chonker -> Mr. Annotator. It includes defensive chunking, nested validation, bounded output, retries, and failure isolation. Source cleanup, provenance preservation, fact durability classification, conservative ownership, semantic-index invalidation, and targeted chapter reanalysis are complete. Crown of Claws structured entities, appearances, facts, proposals, aliases, canon export, and incremental synchronization are complete.

The current lore pipeline deliberately distinguishes raw manuscript material from structured analysis. `pipeline/prechunker.py` creates chapter Markdown, `pipeline/chunker.py` extracts frontmatter and scenes while preserving nearby headings, `pipeline/sync.py` plans changed sources using hashes and pipeline versions, `pipeline/proposal_pipeline.py` writes source-derived SQLite records, and `pipeline/ingest.py` sends Markdown below `canon/` to the semantic index. Canonical analysis input is the chapter corpus, not an arbitrary raw manuscript file.

## Shared memory and retrieval foundation

Memory domains, separate lore and assistant memory, assistant CRUD, validated memory types, retention and status values, provenance, soft forgetting, correction, and compact public references are complete. Assistant memories remain under human control. Explicit memory commands can remember and forget; forgetting is a soft status transition preserving provenance and historical identity.

Durable memory proposals have a review lifecycle. Proposals preserve evidence and approval linkage, use deterministic normalized identities, reinforce equivalent pending evidence, prevent duplicate evidence, support inspection, and provide confirmation-gated bulk approval. Approval creates one canonical assistant memory transactionally and links the proposal to the approved memory. A proposal is not an active memory until the normal approval path completes.

The association graph is domain-scoped and currently provides explainable one-hop retrieval context. Deterministic retrieval, diagnostics, benchmark fixtures, lexical/semantic/no-match metrics, fixture-only deterministic/semantic/hybrid comparisons, semantic cutoffs, and ambiguity-margin calibration are complete. Conversational memory introspection is limited to active canonical memories and approved provenance. Semantic and hybrid retrieval remain explicit evaluation dependencies rather than an automatic chat policy until benchmark evidence supports them.

Assistant retrieval is injected through the `MemoryRetriever` boundary. `AssistantSession` and `AssistantApplication` do not own an unreplaceable retrieval implementation. The production default preserves deterministic SQLite and association ranking; future opt-in semantic or hybrid chat retrieval must be benchmark backed. Context assembly is deterministic and read-only: selected records, document chunks, persona state, policy, capability context, and diagnostics are assembled into bounded model messages without retrieval or database mutation inside the context renderer.

## Persona Runtime

The Persona Runtime has three state layers. Static identity includes explicitly configured stable facts such as name, species, core values, ethics, boundaries, relationship framing, and speech identity. Dynamic personality contains slower traits such as interests, habits, familiarity, trust, skill confidence, preferences, curiosity, and communication tendencies. Every dynamic change must have a source, reason, timestamp, bounded rate of change, and inspectable history. Momentary state contains short-lived mood, energy, attention, current activity, focus, urgency, social availability, and emotional response. Momentary state is derived from recent authorized events and decays; it must not become permanent memory without an explicit observation or proposal path.

The runtime produces a bounded `BehaviorContext`, not a final answer. Identity, dynamic traits, momentary state, active visible memories, attention selection, and behavior rules produce a compact context packet for `ContextManager`, which then calls a provider. Model instructions are advisory and never a security boundary. Values that must remain private, numeric, provenance-sensitive, permission-sensitive, or structurally protected are sanitized before prompt assembly and replaced with bounded intent-level or qualitative context. The model cannot be trusted to redact a protected value after seeing it.

The file-backed persona layer, neutral fallback, separate engine policy, read-only context manager, bounded session context, streaming, clean interruption rollback, context statistics, phase timing diagnostics, and runtime model selection are complete. Murr remains the active stock startup persona, with neutral and Nova also available as declarative packages. The legacy `persona/default.md` path is storage only; the public identity is the configured persona ID. Persona switching is explicit and session-scoped, clears recent conversation context, and leaves shared memory, providers, tools, permissions, configuration, and other sessions untouched.

The core capability registry supplies stable capability IDs and conceptual descriptions. Explicit help questions receive selected capability entries; ordinary chat does not receive the entire manifest. Capability grounding must repeat registered user controls exactly and cannot invent proposal contents, approval steps, alternate commands, private memory access, or unsupported features. CLI, OpenWebUI, TUI, dashboard, and apartment surfaces should stay synchronized through the same Core capability metadata.

## Persona interests, learning, emotion, and relationships

Persona-local development is namespaced and distinct from human-controlled assistant memory. The target persona-local layout contains specific memory for structured lessons and self-observations, semantic memory for embeddings of persona-learned material and approved references, and associative memory linking interests, skills, lessons, outcomes, and contexts. Separate physical databases or Chroma collections are optional packaging optimizations; namespace isolation is mandatory.

The completed Stage 3 foundations provide immutable persona-namespaced interests, bounded verified skills, explicit learning records, RSS/reference intake records, and a pre-execution learning sandbox contract. An interest signal may raise one declared curiosity signal but cannot create expertise, run a network request, execute work, write user memory, or alter prompts. A learning record contains source, hypothesis, isolated attempt, result, verification evidence, timestamp, and optional target skill. Only an explicit verified-success record with evidence may reinforce a skill. Failed or inconclusive attempts remain evidence and never establish expertise. The default sandbox denies execution; ordinary subprocesses are not falsely presented as isolation.

Emotion and real-world relationship foundations are deterministic and explicit-signal-only. Momentary-state derivation accepts authorized interaction, system, or approved-context signals and stays ephemeral. State transitions use decay, hysteresis, and rate limits. Real-world relationship derivation handles bounded familiarity, trust, and evidence confidence without ordinary-chat inference, persistence, canonical facts, prompt mutation, or adventure mixing. The behavior mapper deterministically converts an existing `BehaviorContext` into bounded presentation controls. Future stat-evolution profiles must define signal types, baselines, gain/loss formulas, decay, asymptotes, hysteresis, rate limits, and inspectable explanations; Core calculates them, not the model.

## Multiple personas and shared memory

Multiple declarative persona packages can use shared Core memory while retaining separate runtime state and restricted visibility. Persona visibility combines minimum confidence thresholds with allowed scopes such as personal, preference, project, relationship, routine, and explicit roleplay. The decision occurs after retrieval, preserves ranked order, and never mutates memory. A new persona can default to a lower confidence threshold or narrower scope so it does not immediately know everything, while a future UX may make those policies configurable. Shared factual truth remains separate from persona-local interests, self-memory, relationships, and runtime state.

The future system supports separate resident apartments, persona switching without memory contamination, safe persona-local memory, and eventual multi-persona discussion or Council Mode. A temporary shared discussion environment may seed bounded events and replay metrics, but it must not become unrestricted cross-persona memory or production state.

## Adventure and CYOA engine

Adventure workspaces are isolated `adventure:<id>` namespaces, not another form of personal memory. Each workspace has a registry record and manifest, an append-only validated event log, rebuildable projections, bounded replay context, optional transcript, and future state/resource stores. Adventure relationships and emotions never alter real-world persona or user relationships. Character `knows`, `believes`, and `uncertain` claims are character perspectives, not automatically objective world truth.

The authoritative event log preserves choices, discoveries, promises, lies, relationship changes, emotional transitions, state changes, unresolved hooks, locations, inventory, resources, character knowledge, and other continuity-critical facts. Derived state and snapshots are rebuildable accelerators. Event-log validation covers schema-v1 and schema-v2 compatibility, active-event resolution, typed mutation envelopes, supersession, retraction audit events, resource catalogs, request-ID idempotency, advisory locks, pending-log recovery, manifest reconciliation, and atomic append behavior. A correction preserves original history and only changes which active projection applies; retraction creates a Core-owned no-mutation audit record rather than deleting history.

The adventure session mount supplies complete event-backed state, relationships, knowledge, resources, and separately bounded prompt selections. Prompt limits may constrain context but never authoritative state. The replay selector preserves the first event, high-value continuity categories, and recent facts within a bounded chronology. Adventure turns stage up to sixteen validated ordinary or typed records in memory and commit them as one request-ID-protected batch. Abort, interruption, mount changes, and lifecycle cleanup discard staged values. Ordinary narration never automatically becomes a canonical event.

Current exact controls include adventure list, create, inspect, load, resume, begin, restart fresh, restart established from a checkpoint, status, events, state, relationships, knowledge, resources, pause, end, unload, correction inspection, retraction, immediate typed writes, and staged-turn begin/status/commit/abort. Core-owned adventure commands take precedence over model generation, including malformed commands in the reserved `adventure` namespace. Starting or ending story state clears recent context; pause and end preserve the append-only workspace.

NPC and party-member memory is intentionally lighter than a full StarFur assistant memory subsystem. Their normal context is a bounded derived view of authoritative adventure events, character-specific knowledge, allowed relationship facts, and permitted public resources. A later participant-local salience cache may retain a small number of important memories, but it must be adventure-scoped, inspectable, rebuildable or provenance-backed, and never silently become shared user memory. A persona such as Murr can participate as a party member with initiative, interests, emotional presentation, and bounded action proposals; Core validates and commits any consequences.

The transcript layer is separate from story truth. `transcript.jsonl` records what was presented, with bounded user/narrator roles, sequence IDs, timestamps, explicit Core provenance, advisory locking, and atomic replacement. Exact `adventure transcript` inspects a bounded tail, and exact `adventure transcript record <user|narrator>: <text>` explicitly records one line. Transcript records do not establish events, state, replay facts, memories, or prompt context. Automatic capture, retention policy, and narrative extraction remain future work.

Reviewed document import now has a non-canonical staging boundary. `pipeline.adventure_import` preserves selected server-validated document candidates plus bounded source/chunk provenance under a registered adventure workspace. `POST /v1/starfur/documents/adventure-import` requires an exact existing adventure title, original review ID and candidate IDs, and confirmation `stage reviewed adventure import`. Matching retries are idempotent. Staging creates no event, state, replay fact, prompt context, assistant memory, proposal, or model call. A later typed import-review and commit policy will determine how a selected `details.md` or exported conversation becomes adventure state.

Future adventure work includes replayable regenerated prose around established key events, explicit branching and checkpoint saves, long-session recovery, contradiction handling, automatic but policy-governed narrative extraction, deterministic simulation while the user is away, relationship consistency, resource and inventory rules, and bounded offline catch-up. The authoritative full state must remain separate from bounded model-context projections so context limits can never cause state loss.

## Document intake and RAG

Large external text follows bounded validation, structural prechunking, shared chunking, provider-backed annotation, provenance, review, and explicit handoff. The intake pipeline supports Markdown and text, deterministic profiles such as `assistant_note`, `technical_document`, and `adventure_state`, heading and state-boundary preservation, resilient per-chunk failures, stable candidate identities, short-lived review sessions, source-scoped context packets, and an optional OpenWebUI Filter. OpenWebUI uploads are intercepted for the StarFur model so source text remains distinct from the user request and built-in RAG does not contaminate command routing.

Terminal annotation supports an opt-in progress transport: `POST /v1/starfur/documents/annotate?stream=terminal` emits only completed/total chunk counts followed by final review JSON. Standard API JSON remains unchanged for OpenWebUI. Remaining intake work includes selective/query-driven annotation, asynchronous or pollable processing, multi-file and non-text ingestion, semantic indexing, richer UI review controls, canonical manuscript integration, and a real provider router. A 40-chunk story may still be slow because the current path is bounded but largely sequential and the default annotation profile can fall back to Qwen.

## Provider registry and model routing

Ollama is the current chat and embedding implementation. The provider protocol already supports replaceable chat adapters and legacy fake clients. Capability interfaces are planned for chat, embedding, vision, image generation, speech transcription, and speech synthesis. Hosted APIs, LM Studio, llama.cpp, ComfyUI, Stable Diffusion, TTS, and STT should be adapters rather than Core special cases.

Declarative task profiles already name workloads such as assistant chat, assistant proposal extraction, document annotation, retrieval evaluation, coding, vision, image generation, and speech. Profiles validate provider/model/options/context-size declarations but are not yet an automatic router or fallback engine. The next routing stage must create a provider-neutral registry of available capabilities, start with deterministic task and intent rules plus explicit user overrides, select a specialist annotation model when appropriate, and use heavier fallback models only when benchmarks justify them. It must record route confidence, selected task/provider/model, fallback reason, load/unload behavior, latency, TTFT, resource use, and route stability. A small routing model should be introduced only if deterministic rules prove insufficient.

Routing must preserve continuity in Core. A model can be swapped without changing persona identity, canonical memory, adventure state, permissions, or diagnostics. The router selects a provider and workload profile; Core owns context assembly, policy, validation, writes, and result integration. Annotation throughput will eventually benefit from a fast specialist model, bounded parallel chunk work, resumable jobs, skip/reuse of already annotated chunks, and asynchronous progress—not from routing alone.

## Tools, permissions, perception, and apartment

The tool stage will add a structured registry and permission engine with allow-once, always-allow, deny, and confirmation-required policies. Filesystem, system status, scheduling, watchers, process, network, external services, and autonomous learning experiments remain individually permissioned and audited. No tool may silently modify production files, memories, or external systems.

Vision begins with one-shot screen, window, region, image, and PDF inspection. Later media adapters provide image generation, TTS, STT, voice-activity detection, transcript confidence, interruption/barge-in behavior, notifications, and ambient apartment features. Continuous surveillance is not the default. Providers remain optional and replaceable.

The first apartment prototype is a low-resource read-only visualization consuming public snapshots: active persona identity and state, provider lifecycle, loaded adventure/status, safe diagnostics, and permission prompts. A workbench can represent active projects, a bookshelf installed models, a newspaper feeds, a calendar schedule, a window permissioned desktop state, and frames commissioned or procedural artwork. Placeholder assets must use stable IDs so human-made art can replace them later. The apartment is not a new memory store, world-state authority, or permission bypass.

The eventual zero-provider mode keeps StarFur useful as a deterministic desktop companion or fox simulation even without an LLM, vision model, TTS, image model, or speech provider. Authored dialogue, schedules, animations, relationship/state continuity, system indicators, and human-made art can continue while model providers are unavailable. Provider lifecycle state should let the apartment show connecting, loading, ready, thinking, streaming, idle, cooling, unloading, and error without parsing prose.

An opt-in idle adventure scene display may later detect permissioned inactivity, summarize current structured adventure state, generate a cached illustrative image, and show it in an apartment frame or overlay. It must debounce generation, react to user activity, respect privacy/resource modes, and never treat generated imagery as canon. Procedural adventure visuals are much later than authoritative simulation and replay.

## Portable adventures, Workshop, and Steam

The first useful distributable adventure should be a small data-only `.starfur-adventure` archive containing a validated manifest, `details.md` or equivalent structured state, and optionally an exported conversation or transcript plus bounded assets. Workshop is a distribution adapter over the same validator and importer. Installed package content is immutable; event/state history and user-local memory are separate save data. Packages must be versioned, replayable across compatible Core versions, reject invalid or incompatible members safely, never execute code, and never grant permissions.

Creator tooling will eventually let non-programmers create personas, adventures, characters, resource catalogs, apartments, voices, animation, and tools through forms and editors rather than Python or hand-edited JSON/YAML. Steam productization requires a polished installer, backups, migrations, local packages, Workshop access, accessibility, controller support, offline operation, safe updates, and a low-cost convenience version while the open Core remains available. A StarFur Ready artist ecosystem can provide commissioned sprites, layered rigs, voices, apartments, and character packs with stable runtime compatibility.

## Research and evaluation

StarFur maintains a reproducible behavioral benchmark layer above unit and integration tests. Benchmark runs should record benchmark/schema version, git commit, provider/model/quantization, context size, hardware and resource profile, test case, expected and actual results, pass/fail, retrieval IDs/scores/reasons, latency, TTFT, and bounded CPU/RAM/VRAM/temperature metrics when available. Real failures should become permanent regression cases.

Initial benchmark families cover memory retrieval Recall@K and Precision@K, false positives and no-match cases, retrieval success separately from model answer/use success, long-document RAG at increasing sizes, annotation/proposal extraction and false positives, prompt-contamination boundaries, persona and instruction adherence, provider/model portability, latency and resource utilization, and long-session/restart/recovery behavior. A small-model scaling benchmark holds the surrounding architecture constant while varying model size and quantization; it separates externally supplied memory/retrieval performance from reasoning, instruction following, persona quality, and prose quality. Later ablation compares full StarFur to configurations with individual cognition components disabled and to a raw-model baseline.

The experiment ledger is local, append-only, privacy-aware, and useful without retaining unrestricted conversations. Required future tools include deterministic suites, router decision traces, reproducible run manifests, comparison reports, and exportable research summaries. The data should support engineering decisions, technical validation, grant applications, and a public engineering portfolio rather than collecting metrics without a hypothesis.

## Future Crown of Claws writing environment and research

The writing environment will add POV and perspective metadata for Murr, Quiet Accord, and third-party viewpoints; character knowledge state; revelation management; timelines; contradiction checks; continuity analysis; and writing-partner mode. It should reuse the same structured-memory, provenance, retrieval, and context boundaries as the resident platform.

Future research includes temporal and multi-hop associations after one-hop retrieval is benchmarked, explicit emotion and state-decay explanations, retrieval compression only after long-duration prompt metrics justify it, autonomous learning and replayable companion regression benchmarks, permissioned proactive assistance, native media perception/generation, deterministic procedural adventures with persona-driven decisions, cached apartment scene rendering, Workshop distribution, licensing, and companion packaging.

## Additional details from ROADMAP.v4 comparison proposal

ROADMAP.v4.md is an expanded successor proposal and comparison document, not the authoritative roadmap. Its status legend distinguishes COMPLETED implementation backed by focused tests, FOUNDATION narrow primitives that are not complete product behavior, ACTIVE dependency-gated work, LATER ordered work with prerequisites, and RESEARCH ideas that lack enough evidence for a committed product design. The v4 proposal was designed against repository evidence and the baseline roadmap; discrepancies must be called out rather than silently reconciled.

The v4 proposal adds eight non-negotiable rules. Core is authoritative for permissions, memory boundaries, commands, state transitions, adventure resources, and hidden values before prompting. Models are untrusted providers: output can become a proposal or staged mutation but never an authoritative write merely because a prompt asks for compliance. Full canonical state is never identical to prompt context; deterministic selectors create bounded labeled projections. CLI, OpenWebUI, TUI, dashboard, apartment, phone, and Steam clients use shared services. Packages are versioned declarative data by default; executable extensions require a separately permissioned plugin design. Shared user memory, lore, persona-local learning, roleplay-scoped memory, and `adventure:<id>` state remain independently inspectable. Automatic changes require provenance, policy, validation, outcome, and correction or recovery. Evidence precedes claims: tests prove mechanics, while versioned behavioral benchmarks measure model-dependent reliability.

The proposed ownership model keeps Core responsible for canonical memory, retrieval, persona runtime, provider routing, permissions, tools, adventure state, package validation, migrations, and audit events. Persona packages own declarative identity and presentation defaults, not tools or permissions. Provider adapters translate to external model APIs and expose supported health/model metadata, but do not own session policy or canonical writes. Presentation clients render shared public snapshots. Adventure packages declare data, resources, and content but cannot execute code or grant access.

The v4 evidence review records several implementation facts that are easy to lose in a broad summary. `pipeline/context.py` owns deterministic message assembly and token estimates. `pipeline/application.py` owns the presentation-neutral facade and bounded per-conversation isolation. `pipeline/providers.py` and `pipeline/provider_state.py` own provider contracts and lifecycle state. `pipeline/task_profiles.py` is declarative workload configuration, not an automatic router or fallback engine. Document intake is bounded, structural, provider-backed, review-based, and currently synchronous; it supports one text attachment in the Filter path, ephemeral review storage, no canonical multi-file workspace, and no production semantic document index. Benchmark, persona, and adventure behavioral suites still need to grow even though many mechanical foundations are complete.

### Expanded dependency stages

Stage A is adventure integrity and authoritative projections. A1 separates complete rebuildable projections from bounded prompt selectors and requires tests proving that more than twelve state keys survive reload while only a deterministic subset enters context. A2 hardens registry, manifest, event-log, pending-file, orphan-workspace, and cross-process recovery with failure injection, writer races, retry idempotency, malformed tails, and reconciliation. A3 introduces typed schema-v2 mutation envelopes while preserving schema-v1 logs and keeping narrative summary separate from mutation payloads. A4 commits ordinary events, state, relationships, knowledge, and resources atomically. A5 keeps malformed reserved Core namespaces out of model generation. Much of A1 through A5 has a foundation or initial slice, but broader recovery and migration policy remain prerequisites for automatic narrative extraction.

Stage B provides generic adventure state without turning Core into a game-specific engine. Scenario packages declare resources using generic flags, bounded integers/decimals, inventories, equipment slots, objectives, locations, and clocks. Names such as ammo, credits, health, or mana remain package data rather than Core concepts. Corrections, retractions, supersession, contradiction inspection, checkpoints, fresh restart, established-premise restart, branch isolation, and replay are separate concerns. Stage B4 governs party-member initiative: a persona or NPC receives an adventure-local bounded view, a provider may propose an action, and Core validates typed consequences before narration, TTS, animation, or apartment presentation. Initiative is disabled or explicitly trigger/cooldown limited by default.

Stage C is the safe narrative-to-state loop. C1 binds one workspace, roleplay session, and active branch. C2 keeps transcript, canonical event history, authoritative projections, and derived narrative memory distinct. C3 permits a task-specific provider to propose events or mutations from a completed turn, but Core validates source, schema, resource operations, contradiction policy, salience, namespace, and confidence. Low-risk high-confidence continuity may eventually auto-commit under strict policy; uncertain or high-impact candidates remain visible for review. Decorative prose, model inventions, and hidden reasoning never become canonical automatically. C4 imports reviewed story documents into a selected adventure, preserves source/chunk provenance, stages typed candidates, and eventually supports multi-file imports, asynchronous progress, resume/retry, and bounded failure reporting.

Stage D is continuous behavioral evaluation. Existing fixture slices cover complete structured projections, bounded replay, context-limit separation, resources, public/hidden resource isolation, invalid operations, and checkpoint-derived child prefixes. Remaining fixtures must cover command/lifecycle behavior, corruption and recovery, relationship consistency, restart, and a dedicated bounded adventure-result ledger. Claims that small models behave like larger models require recorded behavioral results rather than unit-test success alone.

Stage E is the provider registry and measured routing stage. It should convert task profiles into a provider-neutral registry of chat, embedding, vision, image, speech, and specialist capabilities; validate model and capability availability; route deterministic task categories with explicit user overrides; and add a small routing model only if benchmarks show that rules are insufficient. It must handle unavailable providers, timeout, empty output, fallback loops, context-size limits, load/unload, user override, route confidence, route stability, and diagnostics accuracy. A coding or image request should return through the same session without changing persona, memory, or authority. Routing must be stable before broad tools and media.

Stage F is the permissioned tool engine. Every filesystem, process, screen, network, scheduler, watcher, or external-service action receives allow-once, always-allow, deny, or confirmation-required treatment. No background tool or Workshop package gets ambient authority. Stage G adds one-shot perception and media after routing and permissions: inspect a window or image, generate a scene, transcribe audio, synthesize speech, detect voice activity, report confidence, and support cancellation and barge-in. Continuous monitoring is opt-in and visible.

Stage H is the apartment/dashboard prototype. H0 consumes public snapshots through a low-resource read-only surface. H1 renders persona identity/state, current activity, provider lifecycle, loaded adventure, task progress, safe diagnostics, and permission prompts with stable placeholder asset slots. H2 adds sprites, animation, expressions, poses, layers, and accessibility fallbacks without changing Core identifiers or save data. H3 adds permissioned idle scene cards or screensaver images derived from structured state, cached and debounced; later features include voice, notifications, calendar/feed displays, and system monitoring. Generated visuals remain illustrations, never authoritative events.

Zero-provider resident runtime is a cross-cutting release requirement. A no-provider installation must boot a persona, restore allowed persistent resident state, run deterministic activities and reactions, render human-authored assets, and expose settings and inspection controls. Removing, unloading, swapping, or failing an optional provider must preserve persona identity, resident continuity, and apartment state while reporting only the affected capability as unavailable. Tests include no-provider startup, unavailable provider startup, provider swap/unload while active, seeded deterministic behavior, authored-dialogue fallback, missing optional-media assets, restart continuity, and an assertion that no provider call is attempted in zero-provider mode.

Persona-local continuity is also cross-cutting. It must distinguish durable persona-local relationships, development evidence, interests, skills, milestones, and meaningful interaction timestamps from reconstructable transient mood/energy/attention and session-ephemeral response planning. Restart reconstructs transient state with deterministic elapsed-time decay instead of freezing stale literal values. Optional user-local presentation overlays can alter bounded expression defaults without granting permissions, changing installed packages, or altering shared memory; disabling or removing an overlay preserves accumulated continuity. Missing or malformed overlays fall back safely.

Stage I is Steam and Workshop productization. Package manifest v1 should include stable package ID, semantic version, schema version, Core compatibility range, display metadata, author/license/attribution, locale, tags, optional dependencies, declared capabilities and asset slots, normalized relative paths, hashes, size limits, fallback assets, and migration metadata. Installation validates in quarantine, rejects traversal, symlinks, oversized archives, and executable content by default, and activates atomically. Installed content is immutable while saves, persona-local state, and shared memory remain separate. The Steam Workshop adapter must remain a distribution adapter over the local validator rather than a Core dependency. Release engineering includes first-run setup, provider discovery, save paths, migration, backup/restore, crash recovery, log redaction, accessibility, controller input, offline behavior, update compatibility, uninstall choices, and clean-install/update/rollback/corruption/missing-provider/missing-asset smoke suites.

Stage J is resident autonomy and simulation research after earlier gates pass. It includes permissioned scheduling and watchers, durable persona-local learning with verified experiments, deterministic offline adventure simulation using structured time and resources, provider calls only for meaningful decisions or narration, procedural/generated adventures and visuals, temporary shared-state Council Mode, and Crown of Claws writing-partner analysis. These are research directions until the authoritative state, permission, persistence, routing, and benchmark gates are satisfied.

## End state

StarFur is intended to be an operating environment for persistent AI companions. Users should sit down at a computer where an intelligent resident already lives, remembers responsibly, develops verified interests and skills, responds through a coherent evolving personality, participates in persistent adventures, uses tools with permission, remains useful across providers and restarts, and stays transparent and user-controlled. The language model may change; the resident continuity, memory boundaries, state, apartment identity, and user trust remain stable.
